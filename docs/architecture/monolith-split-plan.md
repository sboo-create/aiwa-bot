# Распил aiwa_bot.py: модульный монолит

Решение владельца от 2026-07-31 (по итогам разбора архитектуры): сервисы не
разделяем — процесс, деплой и SQLite остаются как есть. Меняется только
организация кода: `aiwa_bot.py` (12,7 тыс. строк, 65% кодовой базы)
постепенно переезжает в пакет `aiwa/`.

## Паттерн переноса

1. Код переносится **механически** — без переименований, без «улучшений по
   пути». Один модуль = один PR = одна выкатка через deploy workflow.
2. В `aiwa_bot.py` на месте перенесённого блока остаётся реэкспорт:
   `from aiwa.<module> import (...)`. Все прежние ссылки — из соседнего кода,
   из тестов, из `bot.X` — продолжают работать.
3. Перенесённый код обращается к ещё-не-перенесённому состоянию **через
   модуль**: `import aiwa_bot as bot` и `bot.db()`, `bot.dtoday()`, а не
   через прямой импорт имён. Это сохраняет работоспособность monkey-patching
   в тестах (`bot.DB = tmp`) и разрывает проблему циклического импорта:
   к моменту вызова функции модуль `aiwa_bot` уже инициализирован.
4. Гейт каждого PR — полный существующий тест-suite (383+). Никакой перенос
   не считается завершённым, пока не выкачен и health не подтверждён.

Отложено сознательно (в aiwa_bot.py остаются):

- **api** — зона несмежная: хендлеры перемежаются worker-функциями с
  `global`-состоянием (семафоры, задачи food-assets/AI). Перед переносом
  нужно перегруппировать исходник (worker-блоки отдельно) — отдельный
  механический PR;
- **events-writer** — функции переприсваивают глобальное состояние потока
  (`global _EVENT_WRITER_*`), которое читает `/health`; переносить только
  вместе с точками чтения;
- **db-слой и helpers** — на них смотрит весь код; переносятся последними,
  когда остальное уже в пакете;
- **workers/on_startup/run_all** — ствол процесса, остаётся в aiwa_bot.py.

Итог первой волны: монофайл 12 729 → 8 484 строк (−33%), в пакете 8 модулей
(~4 600 строк). Уроки, закреплённые в экстракторе: alias `_bot` (параметр
`bot` у сендеров затенял модуль), scope-aware AST-префиксация (semantics
монолита + monkey-patching тестов), def-time позиции без префикса,
конвертация байтовых col_offset в символьные (кириллица).

После завершения всех волн в `aiwa_bot.py` остаются: конфиг, сборка приложения,
`run_all()`/`main()` и реэкспорты (~600 строк). Реэкспорты можно будет
постепенно убирать, переводя вызовы на прямые импорты — отдельными PR.

## Чего не делать при переносе

- не менять сигнатуры и поведение (даже «очевидные» улучшения — отдельным PR);
- не переносить два модуля в одном PR;
- не создавать `aiwa/utils.py` — свалка хуже монофайла;
- не убирать реэкспорт, пока на имя есть хоть одна внешняя ссылка.

## Постмортем волны 1 (2026-07-31, откачена)

Волна выкачена ночью, откачена утром: в 05:00 UTC упала ежедневная
рассылка сводки — `NameError: name 'bot' is not defined` в
`aiwa/pushes.py`. Внутри **f-строки** префикс превратился в `bot.` вместо
`_bot.`: tokenize/untokenize в Python 3.12 (PEP 701 токенизирует
внутренности f-строк) исказил подмену NAME-токена внутри строки.
Health был зелёным (процесс жив), алертинг молчал — ломались только
рантайм-пути, не покрытые тестами.

Правила для волны 2 (обязательные, без исключений):

1. **pyflakes на каждый сгенерированный модуль** — ловит такой NameError
   мгновенно (в волне 1 проверили только keyboards);
2. запрет f-строк с выражениями в переносимых блоках: перед экстрактом
   выражения выносятся из f-строк, либо rewriter обходит FSTRING-токены
   и правит их отдельной строковой заменой с верификацией;
3. смоук, который ВЫЗЫВАЕТ каждый перенесённый публичный callable
   (хотя бы конструирование аргументов и NameError-пробу через dis/exec);
4. канареечный деплой днём с часом наблюдения, не ночью перед cron 05:00;
5. health должен подсвечивать ошибки job-queue (счётчик handler errors),
   чтобы алертинг ловил тихие NameError в фоновых задачах.
